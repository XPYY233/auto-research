# 工作区迁移

关联 GitHub #2、#10。迁移使用独立暂存目录，逐项登记论文、文档、图像和历史输出路径，比较文件哈希与科研记录后才原子发布。原工作区不修改；已存在的目标绝不覆盖。

维护者在开发环境执行：

```sh
.venv/bin/python scripts/migrate_workspace.py --source /path/to/old-workspace --destination /path/to/new-workspace
```

这一步只准备副本，不改变 App 的日常目录设置。迁移报告包含私人路径，随工作区保留，不提交 GitHub。私人数据库、加密历史、密钥及不可变官方包仍属于 Application Support；本命令不复制或改写它们。跨机器不得复用本机 API 凭据。

## 保护与恢复

- schema v12 校验、SQLite 一致性备份、所有非派生表逐记录比较；仅五个登记路径列允许不同。
- 原文、图片与数据库登记哈希必须一致；不通过更新哈希绕过来源冲突。
- 缺失必要 PDF 或图片、活动提取记录、额外未登记数据库、符号链接、源在复制期间变化均停止发布。
- 已经缺失的非必要历史输出单独登记，保留原历史记录。JSON 内嵌历史路径保持原字节，不进行全库替换。
- 进程中断只留下 `.目标名.migrating-*` 暂存目录；正常重试使用新暂存目录。确认无运行迁移后，维护者可以另行归档或清理遗留暂存区。
- 原子发布使用已验证的 macOS `renamex_np(RENAME_EXCL)`；文件及目录同步后发布，目标已存在时失败。
- 切换日常目录仍须关闭 App、复核迁移后是否新增数据、验证私人状态及断点兼容，并保留原 selector 回退材料。当前命令不提供自动激活。

## 2026-09-19 真实演练

当前真实资料库的迁移被来源哈希检查阻止；未生成可激活目标。27 条论文记录的 `papers.pdf_sha256` 与当前 PDF 不符，而同篇 `documents` 已登记当前 PDF 的哈希。这是既有来源版本关系不一致，不能推断成文件损坏，也不能将“复制字节一致”当成“历史来源已恢复”。保护归档中仍保留两类登记值。详细取证保留本机，GitHub #10 跟踪解决。
